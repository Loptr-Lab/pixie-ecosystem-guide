### Durable model and token lifecycle

Add a separate versioned private store beside configured PIXIE_DATA_FILE on existing `/data`, never in public assets, workspace exports, browser storage, `identity.enc` schema or the hashed-grant configuration. Proposed records:

- `transactions`: hashed transaction handle, browser binding, client/redirect/resource/scope/S256 challenge, opaque original state, preliminary/final consent stage, expected DID if set, expiry. TTL 10 minutes.
- `codes`: SHA-256 of independently generated 256-bit random code, transaction/grant/DID/client/redirect/resource/scope/challenge bindings, expiry (60 seconds), used marker. Atomic consume plus token creation; concurrent redemption has one winner. Invalid PKCE/binding never produces tokens; rate-limit attempts. Retain used-code tombstone briefly for replay detection without retaining raw code.
- `grants`: opaque ID, DID, client and registration revision, resource/scope, consent version/timestamp, absolute expiry, status/revokedAt; no private project contents.
- `access`: SHA-256 of fresh 256-bit token, grant/client/DID/issuer/resource/scope, issuedAt/expiry (proposed 15 minutes). Opaque records replace JWT/JWKS complexity for co-located issuer/resource server. Validation checks issuer exact match via record provenance, exact audience/resource, scope, expiry, active client and active grant on every request; hashes alone are not authorization.
- `refresh`: independent 256-bit token hash, grant/family/generation, expiry (proposed 7-day absolute grant lifetime), used/revoked tombstones. Rotate atomically every use, bind client/resource and restrict scope to original grant. Replay revokes the whole family and associated access tokens. Retain tombstones through family expiry to detect reuse; never extend beyond absolute grant expiry. No `offline_access` claim is required/invented; refresh behavior is explicitly part of this proposed OAuth grant, not OIDC.

These lifetimes are proposed security policy, not host mandates. Access and refresh credentials must be cryptographically domain-separated in generation/record lookup from codes and legacy/static keys. Never use `PIXIE_MCP_CLIENT_TOKEN_HASHES` for OAuth or accept those credentials in token/revoke endpoints. Retain legacy bearer behavior only for existing callers; no OAuth failure may downgrade to it, browser cookies, Sites headers, anonymous access or a different issuer. The new public OAuth principal cannot be upgraded to a private browser/workspace principal merely because it has a DID.

Reuse `withPrivateFileLock` for exclusive transactions and the existing encrypted-envelope/atomic-write pattern only after targeted security review; `identityStore` is not a generic OAuth grant database. New module/schema/key/AAD namespace required, no migration of existing secrets. Proposed new independent encryption key and feature flag would be provisioned only after separate approval. Write via mode 0600 temp + fsync + atomic rename + parent-directory durability review; validate schema, symlink boundaries, capacities and expiry. Single live writer on current mounted volume only. Lock timeout/corrupt/missing expected state/key failure => OAuth unavailable and no grant, never empty-reset existing state. Do not add replicas/regions or use memory-only codes. Bound transactions/records/request sizes, cleanup and per-client/IP/session abuse limits; fail closed at capacity. Store access checks may serialize disk I/O; measure before release, do not add a DB/host speculatively.

Revocation must be durable and checked on every MCP request/refresh, including after restart. On grant disable or revocation, subsequent requests fail; no claim of cancelling already-running public reads. Browser sign-out and ChatGPT disconnect are distinct events: proposed policy is browser logout ends that session, while explicit connection revoke ends the MCP grant; disclose this and provide revoke control. Do not revoke other users or upstream Atmosphere identity automatically. On uncertain token response, do not mint replacement tokens outside reviewed replay policy. Backup restoration must not resurrect revoked grants: recovery disables OAuth and invalidates old grant/token state (fresh issuance epoch/key policy) before reopening, while preserving workspace/browser data. Rollback must not restore pre-revocation OAuth records as active.
